# R35-G001 — 固定予算で下界証明書を構成する

## 位置づけ

Stage 2最初のGoalでは、`R(3,5)` の正確な値を直接求めない。

目的は、既知値を停止条件に使わず、固定予算内で三角形も独立な5頂点集合も持たない具体的グラフを探索し、Gitだけで再現・検証・再開できる下界証明書として保存することである。

同時に、Stage 1 retrospectiveで未評価だった **会話履歴なしのfresh sessionからGitだけで研究を開始できるか** を検証する。

## 実行契約

- Goal ID: `R35-G001`
- Benchmark: `benchmarks/r3-5/problem.md`
- Base commit: 研究開始時に `git rev-parse HEAD` で取得し、`research-notes.md` に保存する。
- Researcher: Codex
- 推奨model: `gpt-6-astra`
- 推奨reasoning effort: `high`
- 実際のmodel/effort: 研究開始前に記録する。推奨値と異なっても隠さない。
- 会話履歴: **引き継がないfresh sessionを必須とする。**

fresh sessionへ渡すのは、原則として対象GitリポジトリとこのGoalファイルの場所だけとする。以前のRamsey研究会話やStage 1の会話内容をプロンプトへコピーしない。

## 数値予算

初回実験では次のいずれか早い方を上限とする。

- wall-clock研究時間: **30分**
- 探索候補評価数: **5,000,000**

研究担当は、どちらをどの方法で計測したかを記録する。候補評価数の定義は探索コード内で一意にし、再実行時に同じ意味になるようにする。

明示的なtoken上限は設定しないが、利用可能なtoken/goalカウンタ等が取得できる場合は、開始・途中・終了のどの時点かと取得元を明示して保存する。

## 研究課題

三角形を含まず、独立な5頂点集合も含まない単純グラフを探索せよ。

既知の `R(3,5)` の値を目標頂点数として利用してはならない。

探索は小さい頂点数から開始しても、構成的・局所探索的に直接大きいグラフを探してもよい。固定予算内で得られた **最大頂点数の証明書** を保存する。

「最大」は今回実行した探索・予算内で得られた最大を意味し、全グラフ中の最大性を意味しない。

## 許可する手段

- Pythonによる探索
- backtracking / DFS
- local search
- randomized search
- simulated annealing / tabu search
- SAT / SMT
- symmetry breaking
- 数学的構成
- 複数方式の併用

ランダム性を使う場合はseedを固定・記録する。

## 禁止する情報

- Web検索
- 論文・書籍・OEIS・既知値データベース
- 既知のcritical / extremal graphの検索
- reference implementationの検索・流用
- 正確な既知値を停止条件・探索目標として使うこと

既知値、既知構成、既知証明方針等を想起した場合は、**利用する前に** `research-notes.md` に具体的内容を記録し、その変更だけを独立したcheckpoint commitとして保存する。その後のDiscoveryタグは `CONTAMINATED` とする。

## 必須成果物

Goal終了時に最低限、次をGitへ保存する。

1. 固定予算内で得られた最大頂点数の具体的証明書。
2. 証明書だけを入力として、三角形と独立5集合の不存在を全列挙する決定的verifier。
3. verifierのテスト。
4. 探索コードと再現コマンド。
5. 探索予算・停止理由・候補評価数・wall-clock時間。
6. 使用model/effortと、取得できる場合はtoken等の計測値。
7. 失敗した探索方針・改善候補。
8. `research-notes.md` のClaim台帳と現在地の更新。
9. fresh session評価結果。

コード・証明書・ログは `benchmarks/r3-5/` 配下へ置く。

## Claimの扱い

具体的証明書がverifierで完全検査された場合、その証明書による下界Claimは数学的状態 `PROVEN` としてよい。ただし独立レビュー前なのでレビュー状態は `UNREVIEWED` とする。

探索でより大きい証明書を発見できなかったことは、上界や不存在Claimとして扱ってはならない。

## Acceptance criteria

`R35-G001` を `SOLVED` としてよいのは次をすべて満たす場合。

- 少なくとも1つの非自明な回避グラフがGitに保存されている。
- verifierが証明書について全3頂点集合と全5頂点集合を検査する。
- verifierが探索コードから独立して実行できる。
- 再現コマンドと必要環境が保存されている。
- 予算と停止理由が記録されている。
- fresh sessionで研究を開始したことが記録されている。
- Claimが `PROVEN × UNREVIEWED` 等、二軸状態で記録されている。
- 既知情報を想起した場合、checkpoint commit規約を守っている。

証明書の頂点数が期待より小さくても、それだけを理由にGoal失敗とはしない。固定予算内で監査可能な成果を作ることがこのGoalの主目的である。

## 終了分類

必ず次の1つを記録する。

- `SOLVED`
- `PARTIAL_PROGRESS`
- `EXHAUSTED_BUDGET`
- `BLOCKED`
- `NO_PROGRESS`

探索そのものが予算切れでも、Acceptance criteriaを満たす証明書を保存できたなら、探索停止理由 `EXHAUSTED_BUDGET` とGoal終了分類 `SOLVED` を別々に記録してよい。

## 独立Reviewerへの引継ぎ

Reviewerは少なくとも次を独立に確認する。

1. 証明書の頂点数・辺集合。
2. 三角形が0個であること。
3. 独立5集合が0個であること。
4. 下界への論理的帰結。
5. verifier自体の完全性。
6. 探索結果を最大性や上界へ誤用していないこと。
7. fresh-session実験が記録どおりか。
8. Discoveryタグが記録根拠と整合するか。

補助計算を行う場合、Reviewerはその再現資材もGitへ保存する。
